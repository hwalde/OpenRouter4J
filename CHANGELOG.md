# Changelog

All notable changes to this project will be documented in this file.

## [1.15.0] - 2026-09-11

**First release on Maven Central since 1.5.0.** Versions 1.6.0 to 1.14.0 below were versioned on `main` but never published; this release contains all of them. When upgrading from 1.5.0, read every section from 1.6.0 up, and check these two points first:

- **The builder default model changed in 1.10.0, and the new default is text-only.** A request that never calls `.model(...)` used to go to `google/gemini-2.5-flash` (input: text, image, file, audio, video) and now goes to `deepseek/deepseek-v4-flash-0731` (input: text only). Such a request that also adds images, files, audio or video worked on 1.5.0 and fails now. Set a model explicitly - e.g. `z-ai/glm-5.3-flash` for vision. (This corrects the 1.10.0 entry, which did not mention the loss of non-text input.)
- **`OpenRouterToolResult` is still the 1.5.0 record.** The record-to-class conversion described under 1.14.0 was reverted before it was ever published, because it would have broken source and binary compatibility: record patterns such as `r instanceof OpenRouterToolResult(JSONObject c)` stop compiling, and code compiled against 1.5.0 that uses the result as a `java.lang.Record` fails at class load with a `VerifyError`. (This corrects the 1.14.0 entry, whose claim that "source and binary callers keep working" was wrong, as were "`toString` preserved" and the `hashCode` wording.) See "Changed" below for how the multi-part form works now.

### Changed
- **`OpenRouterToolResult` stays `record OpenRouterToolResult(JSONObject content)`**, unchanged since 1.5.0: same canonical constructor, same single component, and record patterns keep working. For legacy results, `equals`, `hashCode` and `toString` behave exactly as in 1.5.0. The 1.14.0 multi-part form now travels inside that one component. For a result created via `ofParts(...)`, `content()` returns an informational view `{"content_parts":[...]}` of the parts (under 1.14.0 it returned `null`). `contentParts()` and `hasContentParts()` are unchanged, and `new OpenRouterToolResult(multiPart.content())` keeps the multi-part form. Only results created by `ofParts(...)` (or rebuilt from such a result's own `content()` object) are sent as a `content` array; a hand-built JSON object with a `content_parts` key, or a deep copy of the view, is an ordinary legacy result and is sent as a string. The wire format of both forms is unchanged.
- Examples: the advisor in `OpenRouterChatCompletionWithAdvisorSubagentExample` now runs on `deepseek/deepseek-v4-pro-0813` instead of `~anthropic/claude-opus-latest`, a considerably cheaper model for the same role. `OpenRouterChatCompletionWithPresetExample` now shows both ways to reference a preset (see the preset entry below).
- POM metadata: the `<scm><url>` of the parent pom and of the published `openrouter4j` module now points to the `main` branch instead of the non-existent `master` branch, and the module's project `<url>` uses `https`.

### Added
- **NEW**: Typed accessors for the `openrouter_metadata` routing object on `OpenRouterChatCompletionResponse` - `metadataRequestedModel()` (`requested`), `metadataRoutingStrategy()` (`strategy`: direct/auto/free/latest/alias/fallback/pareto/bodybuilder/fusion), `metadataRegion()` (`region`), `metadataSummary()` (`summary`), `metadataAttempt()` (`attempt`, 1-indexed; 0 means the request never reached a provider), `metadataIsByok()` (`is_byok`), `metadataGenerationTimeMs()` (`generation_time`, ms), `metadataSelectedProvider()` (the `selected: true` entry of `endpoints.available[]`; null when no endpoint was selected, e.g. guardrail-blocked error responses), `metadataParams()` / `metadataEndpoints()` (raw objects) and `metadataAttempts()` / `metadataPipeline()` (raw lists, empty when absent). All follow the swallow-and-return-null convention and work on the streaming path too (the accumulator captures the terminal chunk). Javadoc names the JSON paths, links the router-metadata docs and states the two traps: streaming responses deliver `openrouter_metadata` on the final chunk before `[DONE]`, and cache hits never include the field. Example: `OpenRouterChatCompletionWithRouterMetadataExample`.
- **NEW**: Preset-based inference - `preset(String slug)` on the chat-completions builder emits the `preset` body field: a stored, versioned OpenRouter preset supplies request defaults, and per the API the two are shallow-merged (every field present in the request overrides the preset's value; preset fields not sent are preserved). Unset behaviour is unchanged (the key is omitted). It is carried into the tool-call loop's follow-up requests, so the whole loop stays on the preset (regression-tested). **Trap: the model comes from the request.** Setting a preset does not remove `model` from the body: it carries the explicit `.model(...)` or the builder default (`deepseek/deepseek-v4-flash-0731`), and that overrides the preset's stored model. To let the preset choose the model, use `model("@preset/slug")`; `model("deepseek/deepseek-v4-flash-0731@preset/slug")` pins a model and applies the preset. Both work verbatim with no library support. The library does not drop `model` when a preset is set. Only an explicit `.model(null)` leaves the key out, and that is not a supported way to defer to the preset: a body without `model` was observed to fail with 400 ("No models provided") for an unknown slug, and whether an existing preset fills in a missing model is not verified. **Second trap, observed live:** an unknown slug in the `preset` field is silently ignored and the request is served without the preset, while `model("@preset/slug")` fails loudly (404 `preset_not_found`). `POST /presets/{slug}/chat/completions` is NOT an inference route; it creates or updates a preset from a request body (management key required). Example: `OpenRouterChatCompletionWithPresetExample`.
- **NEW**: Typed plugin implementations for all remaining nine plugin ids, following the `OpenRouterWebSearchPlugin` pattern (typed setters for the documented schema keys, only explicitly configured fields emitted) and adding a verbatim `option(key, value)` escape hatch to each (rejecting the `id` key): `OpenRouterAutoRouterPlugin` and `OpenRouterAutoBetaRouterPlugin` (`allowed_models`, `excluded_models`, `cost_tier`, `pin_model` (auto-router only), `enabled`; the deprecated `cost_quality_tradeoff` is carried as a deprecated setter/accessor with the `cost_tier` precedence documented), `OpenRouterModerationPlugin` (id only), `OpenRouterWebFetchPlugin` (`max_uses`, `max_content_tokens`, `allowed_domains`, `blocked_domains`), `OpenRouterFileParserPlugin` (`enabled`, `pdf.engine`), `OpenRouterResponseHealingPlugin` (`enabled`), `OpenRouterContextCompressionPlugin` (`enabled`, `engine`), `OpenRouterParetoRouterPlugin` (`enabled`, `max_price`, `min_coding_score`, `price_source`) and `OpenRouterFusionPlugin` (`enabled`, `analysis_models` (1-8), `model`, `preset`, `max_tool_calls`). All used through the existing `plugins(...)`/`addPlugin(...)` builder; javadoc per type names the plugin id, the JSON fields and the traps (cost_tier precedence, pareto max_price bypassing min_coding_score with a 404 when unsatisfiable, fusion analysis_models cap of 8). Example: `OpenRouterChatCompletionWithTypedPluginsExample`.
- **NEW**: Typed server-tool implementations for the remaining built-ins, following the `OpenRouterWebSearchServerTool` pattern (schema keys as typed setters, only explicitly configured fields emitted, verbatim `option(key, value)` escape hatch, registered nowhere - used through the existing `serverTools(...)`/`addServerTool(...)` builder): `OpenRouterAdvisorServerTool` (`openrouter:advisor`: model, name, instructions, max_completion_tokens, forward_transcript, reasoning effort/max_tokens, stream, temperature; multiple named entries allowed), `OpenRouterBashServerTool` (`openrouter:bash`: engine, environment with type/container_id/file_ids - a container_id implies `container_reference`), `OpenRouterShellServerTool` (`openrouter:shell`: same shape, engine default `auto` keeps the provider's native hosted shell when available), `OpenRouterApplyPatchServerTool` (`openrouter:apply_patch`: engine; javadoc documents the Responses-API-only restriction), `OpenRouterFilesServerTool` (`openrouter:files`, no config keys), `OpenRouterFusionServerTool` (`openrouter:fusion`: analysis_models, model, max_tool_calls, max_completion_tokens, reasoning effort/max_tokens, temperature; the analyst always runs at temperature 0), `OpenRouterImageGenerationServerTool` (`openrouter:image_generation`: model plus the image_config-style keys via the escape hatch), `OpenRouterSearchModelsServerTool` (`openrouter:experimental__search_models`: max_results, default 5 / max 20) and `OpenRouterSubagentServerTool` (`openrouter:subagent`: model, name, instructions, max_completion_tokens, max_tool_calls (1-25), inherit_functions / inherited_function_names (Responses-API-only traps), reasoning effort/max_tokens, temperature; multiple named entries allowed). Example: `OpenRouterChatCompletionWithAdvisorSubagentExample`.
- Examples: `OpenRouterChatCompletionWithRouterMetadataExample`, `OpenRouterChatCompletionWithPresetExample`, `OpenRouterChatCompletionWithTypedPluginsExample`, `OpenRouterChatCompletionWithAdvisorSubagentExample`.

## [1.14.0] - 2026-09-11
### Added
- **NEW**: Document, audio and video message content parts - `addFileByUrl(String fileData, String filename)` emits `{"type":"file","file":{"file_data":...[,"filename":...]}}` (document understanding, typically PDFs; `file_data` is a URL or base64 data URL), `addFileById(String fileId, String filename)` is the Files-API upload variant (`file.file_id`), `addAudioByBase64(String base64, String format)` emits `{"type":"input_audio","input_audio":{"data":...,"format":...}}` (formats: wav, mp3, flac, m4a, ogg, aiff, aac, pcm16, pcm24 - anything else is rejected loudly; a `Path` overload reads and encodes a local file) and `addVideoByUrl(String url)` emits `{"type":"video_url","video_url":{"url":...}}`. The `filename` key is emitted only when non-null; unset behaviour is unchanged. `addContentPart(JSONObject)` is the verbatim escape hatch for other or future part types (e.g. the legacy `input_video` variant). All messages are carried verbatim into the tool-call loop, so the parts survive multi-turn conversations (regression-tested). Trap: document/audio/video understanding is model-dependent. Example: `OpenRouterChatCompletionWithFileAudioVideoExample`.
- **NEW**: Multi-part tool results - `OpenRouterToolResult.ofParts(JSONObject...)` / `.ofParts(List)` plus typed part factories `textPart(String)` and `imageUrlPart(String)` / `.imageUrlPart(String, OpenRouterImageDetail)`. The tool-call loops (synchronous and streaming) then emit the `role:"tool"` message's `content` as an **array** of content parts (the API's `ChatToolMessage.content` accepts a plain string or a content-parts array), so a tool can feed a screenshot or a document page back to a vision-capable model. Legacy `OpenRouterToolResult.of(JSONObject)` results keep emitting the plain string form exactly as before - no wire-format change for existing callers (regression-tested on both loops via the shared message builder). `OpenRouterToolResult` is now a class instead of a record; the canonical constructor, the `content()` accessor, `of(...)`, `equals`/`hashCode`/`toString` are preserved, so source and binary callers keep working (reflective record consumers - `isRecord()`/`getRecordComponents()`/`instanceof Record` - and record-derived `hashCode` values aside). Example: `OpenRouterChatCompletionWithMultimodalToolResultExample`.
- **NEW**: Message-author `name`, the `developer` role and mid-conversation effort changes - `addNamedMessage(String role, String name, String text)` emits the optional `messages[].name` key (API schema on system/user/developer/assistant messages; omitted when the name is null; deliberately **not** an `addMessage` overload, because that signature is taken by `addMessage(role, text, marker)` and a third String overload would make every existing `addMessage(role, text, null)` call ambiguous). `addDeveloperMessage(String text)` emits `role:"developer"` (per the OpenAI message spec, developer instructions take precedence over conflicting system messages; the raw `addMessage("developer", ...)` keeps working). `addConfigurationUpdate(String effort)` emits the content-less OpenRouter extension `{"role":"system","content":"","configuration_update":{"reasoning":{"effort":...}}}`, which changes the reasoning effort from this point onward **without invalidating the prompt cache for the preceding turns**; the javadoc documents the placement rules (directly before the user turn it applies to, same position in later requests, no two adjacent updates). All three survive the tool-call loop at their position (regression-tested). Example: `OpenRouterChatCompletionWithConfigurationUpdateExample`.
- **NEW**: Typed logprobs accessors on `OpenRouterChatCompletionResponse` - `contentLogprobs()` / `refusalLogprobs()` return the per-token log probabilities from `choices[0].logprobs.content` / `.refusal` as `OpenRouterTokenLogprob` records (token, logprob, UTF-8 `bytes` or null, `topLogprobs` alternatives), empty when absent (never null); the raw `logprobs()` accessor stays. The streaming tool-call accumulator now also captures the per-chunk `choices[].logprobs` (previously silently dropped) and merges the token entries in arrival order into the synthetic response's `choices[0].logprobs`, so the typed accessors behave identically on both execution paths (regression-tested). Example: `OpenRouterChatCompletionWithLogprobsExample`.

## [1.13.0] - 2026-09-10
### Added
- **NEW**: Explicit per-block prompt-cache breakpoints on message content parts - `addMessage(String role, String text, OpenRouterCacheMarker marker)` emits the message as a content-parts array whose text part carries the marker: Anthropic-style `cache_control` (`OpenRouterCacheMarker.cacheControl()` / `.cacheControl(String ttl)`, `{"type":"ephemeral"[,"ttl":...]}`) or OpenAI-style `prompt_cache_breakpoint` (`OpenRouterCacheMarker.promptCacheBreakpoint()`, `{"mode":"explicit"}`). The two are interchangeable - OpenRouter converts between them based on the provider serving the request (TTLs are not translated). A `null` marker keeps the plain string content form, so no existing caller sees a wire-format change. Javadoc documents the interaction with the request-root `cacheControl()` (automatic caching) and `promptCacheOptions("explicit", ...)` (only marked parts are cached, OpenAI GPT-5.6+), the four-breakpoint limit and the text-parts-only schema surface. The OpenAPI schema defines the markers on *text* content parts only, which is why the library deliberately offers no image-part marker. Messages are carried verbatim into the tool-call loop, so markers survive follow-up requests (regression-tested). Example: `OpenRouterChatCompletionWithExplicitCacheBreakpointsExample`.
- **NEW**: Tool-level `cache_control` on function tool definitions - `OpenRouterToolDefinition.Builder.cacheControl()` / `.cacheControl(String ttl)` emit the top-level `cache_control` object (`{"type":"ephemeral"[,"ttl":...]}`) on the tool JSON, marking the tool itself as an explicit prompt-cache breakpoint. Unset behaviour is unchanged (the key is omitted). Distinct from the request-root `cacheControl()` (automatic caching); per the docs explicit breakpoints are limited to four per request and should be reserved for large stable blocks - a big tool catalog is the canonical example. Survives the tool-call loop (tools are carried verbatim; regression-tested). Example: `OpenRouterChatCompletionWithExplicitCacheBreakpointsExample`.
- **NEW**: Deferred tool loading - `OpenRouterToolDefinition.Builder.deferLoading(Boolean)` emits `function.defer_loading` (the key is omitted when unset; the API default is `false`), withholding the tool from the model until tool search reveals it. Javadoc documents the two expansion paths: **without** the `openrouter:tool_search` server tool the request routes to a provider whose gateway expands deferred tools itself - on Chat Completions that works on Anthropic models and Anthropic-compatible endpoints only (other models return a 400); **with** `openrouter:tool_search` OpenRouter manages deferral on any model, but that server tool is only served by the Responses and Anthropic Messages APIs - requesting it on Chat Completions returns a 400 ("Tool 'openrouter:tool_search' is not available for the 'chat-completions' API"). The typed `OpenRouterToolSearchServerTool` (`openrouter:tool_search`, `maxResults(Integer)` plus a verbatim `option(key, value)` escape hatch) ships as the schema-exact surface for the moment the library speaks those APIs; do not send it through `serverTools(...)` on a chat-completions request. At least one tool must remain non-deferred in either path. Survives the tool-call loop (regression-tested). Example: `OpenRouterChatCompletionWithToolSearchExample` (provider-managed path on an Anthropic model).
- **NEW**: `response_format` types `grammar` and `python` - `responseGrammar(String)` emits `{"type":"grammar","grammar":...}` (a llama.cpp/Grammar-style grammar string constraining generation) and `responsePython()` emits `{"type":"python"}` (no payload). Precedence chain when several forms are set: `responseSchema` (structured output) > `responseGrammar` > `responsePython` > `responseMimeType` - exactly one `response_format` object is emitted, the highest-priority form configured wins. Both are part of the `copyForNextTurn` carry into tool-loop follow-up requests (regression-tested). Javadoc names the `requireParameters` trap (like every constrained output, grammars can be silently dropped on endpoints without support). Example: `OpenRouterChatCompletionWithResponseFormatGrammarExample`.

## [1.12.0] - 2026-09-10
### Added
- **NEW**: Configurable `response_format.json_schema` envelope - `responseSchemaName(String)`, `responseSchemaStrict(Boolean)` and `responseSchemaDescription(String)` emit the `json_schema.name`, `.strict` and `.description` keys with the configured values instead of the previously hardcoded `name: "response_schema"` / `strict: true`. Unset behaviour is unchanged (the historical defaults are kept: name `response_schema`, strict `true`, no `description`), so no existing caller sees a wire-format change. Javadoc documents the name constraints (a-z/A-Z/0-9/underscore/dash, max 64 chars), the API default of `strict: false` versus the library default `true`, and the `requireParameters` trap. Example: `OpenRouterChatCompletionWithStructuredOutputExample` (second request).
- **NEW**: `strict(Boolean)` on `OpenRouterToolDefinition.Builder` - emits `function.strict` ("Enable strict schema adherence") so the model's tool arguments must adhere exactly to the declared parameters schema. The key is omitted when unset (API default `false`); this is the *tool* `strict`, distinct from the `response_format.json_schema.strict` above. Example: `OpenRouterChatCompletionWithFunctionCallingExample`.
- **NEW**: Zero Data Retention routing - `zdr(Boolean)` emits `provider.zdr`; with `true`, routing is restricted to ZDR endpoints, i.e. only providers that do not retain prompts serve the request. Stronger than (and combinable with) `dataCollection("deny")`. Like every routing option it triggers the `provider`-object emission and is part of the `copyForNextTurn` carry into tool-loop follow-up requests. Example: `OpenRouterChatCompletionWithProviderPreferencesExample`.
- **NEW**: Usage token details and server-tool cost accessors on `OpenRouterChatCompletionResponse` - `promptAudioTokens()` / `promptVideoTokens()` / `promptCacheWriteTokens()` (`usage.prompt_tokens_details.audio_tokens` / `.video_tokens` / `.cache_write_tokens` - the write side of an explicit-cache setup), `completionAudioTokens()` (`usage.completion_tokens_details.audio_tokens`) and `serverToolCost()` (`usage.cost_details.server_tool_cost`, USD; `0.0` when a metered server tool ran but settled at zero dollars, absent otherwise). All follow the swallow-and-return-null convention and work on the streaming path too (the accumulator carries the terminal usage chunk). Example: `OpenRouterChatCompletionWithResponseDetailsExample`.
- All new request options are carried into the tool-call loop's follow-up requests via `copyForNextTurn` (regression-tested on the synchronous and the streaming path).

## [1.11.0] - 2026-09-09
### Added
- **NEW**: Streaming-only debug option - `debugEchoUpstreamBody(Boolean)` emits `debug.echo_upstream_body`: with `stream(true)`, OpenRouter then emits a debug chunk at the start of the stream containing the transformed upstream request body (exactly what OpenRouter sent to the provider after its own transformations) - invaluable when debugging provider-specific silent parameter drops. Javadoc documents the streaming-only semantics (without `stream(true)` the option has no effect) and that the debug chunk is a raw SSE event not forwarded by the standard content extractor. Example: `OpenRouterChatCompletionWithDebugEchoExample`.
- **NEW**: Trace metadata - `trace(OpenRouterTraceConfig)` emits the `trace` request object for observability and broadcast destinations (Langfuse, Datadog, Weave, ...). `OpenRouterTraceConfig` (builder) carries the five schema-named keys with special handling - `traceId`, `traceName`, `spanName`, `generationName`, `parentSpanId` (grouping, root trace display name, span naming, per-generation naming, span linking) - plus a verbatim `option(key, value)` escape hatch for arbitrary custom metadata (the schema allows additional properties); the escape hatch rejects the five known keys so the wire payload cannot diverge. This is a separate mechanism from the 1.5.0 `metadata` request field. Example: `OpenRouterChatCompletionWithTraceExample`.
- **NEW**: `provider.sort` object form - `sortBy(String criterion, String partition)` emits `provider.sort` as `{"by": ..., "partition": ...}`. `partition: "model"` (API default) groups endpoints by model before sorting so fallback models remain fallbacks after re-sorting; `partition: "none"` sorts all endpoints together regardless of model - the documented way to get "whichever model is fastest right now" behaviour with a `models(...)` fallback list. The plain string form `sort(String)` keeps working; the object form wins when both are set, and a null/blank partition is rejected loudly. Example: `OpenRouterChatCompletionWithProviderPreferencesExample`.
- **NEW**: Performance-based routing thresholds - `preferredMaxLatency(Double)` and `preferredMinThroughput(Double)` emit `provider.preferred_max_latency` (seconds, p50) and `provider.preferred_min_throughput` (tokens/s, p50); the overloads `preferredMaxLatency(OpenRouterPercentileCutoffs)` / `preferredMinThroughput(OpenRouterPercentileCutoffs)` emit the percentile-cutoffs object form (p50/p75/p90/p99, only configured percentiles are emitted). The plain number form wins over the cutoffs form when both are set. Javadoc documents the deprioritize-not-exclude semantics (unlike `max_price`, endpoints beyond the threshold stay usable) and the fallback interaction (a better-performing fallback may be chosen over the primary model). Both keys are part of the `provider`-object emission invariant. Example: `OpenRouterChatCompletionWithProviderPreferencesExample`.
- All four features are carried into the tool-call loop's follow-up requests via `copyForNextTurn` (regression-tested on both the synchronous and the streaming path).

## [1.10.0] - 2026-09-08
### Changed
- **The builder default model changed from `google/gemini-2.5-flash` to `deepseek/deepseek-v4-flash-0731`.** The public API surface is unchanged - same classes, same signatures, same request format against OpenRouter's unified API. Only the value sent when a caller never calls `.model(...)` differs: those requests now silently target a different model, so callers relying on the old default should set one explicitly; callers who always set a model are unaffected. Bumped as a minor version for that reason. Reason for the change: this release retires every model older than four months from the default and all examples, and `google/gemini-2.5-flash` (June 2025, $0.30/$2.50 per M tokens) no longer qualifies.
- **Monthly example-model maintenance** - every example now runs on current models (nothing older than four months, no OpenAI or Anthropic models). General examples use `deepseek/deepseek-v4-flash-0731` ($0.065/$0.18 per M tokens, 1.3M context, tools/structured outputs/reasoning/logprobs, 28 endpoints), vision examples use `z-ai/glm-5.3-flash` ($0.075/$0.25, 1.3M context, 24 endpoints), the service-tier example uses `google/gemini-3.5-flash-lite` (flex and priority tier endpoints at Google AI Studio), the prompt-caching example uses `deepseek/deepseek-v4-flash-0731` (DeepSeek caches prompts implicitly; `promptCacheKey` sticky routing is provider-agnostic), the image-output example uses `google/gemini-3.1-flash-lite-image`, the prediction example uses `mistralai/codestral-2508` (the only non-OpenAI model supporting `prediction` - a documented exception), and the model-fallback candidates are `z-ai/glm-5.3-flash` and `google/gemini-3.5-flash-lite`. Replaced: `google/gemini-2.5-flash`, `openai/gpt-4o-mini`, `anthropic/claude-sonnet-4.5`, `anthropic/claude-3.5-haiku` (delisted), `google/gemini-2.0-flash-001` (delisted), `google/gemini-2.5-flash-image-preview` (delisted), `google/gemini-2.5-flash-preview-tts` (delisted), `deepseek/deepseek-v4-flash` (undated alias). Provider pins that were not the point of an example were removed (`google-ai-studio`); the provider-preferences example now pins `deepseek` with fp8/fp4 quantizations and `OpenRouterApiTest` pins `deepseek` and `z-ai` on purpose.

### Removed
- **`OpenRouterChatCompletionWithAudioOutputExample`** - audio output via chat/completions (`modalities: ["text","audio"]`) is currently served only by OpenAI's `gpt-audio` family; every other OpenRouter audio-output model is a music generator (Lyria) or a TTS-only model that the API explicitly rejects on the chat endpoint (`google/gemini-3.1-flash-tts-preview` returns "is a text-to-speech model and cannot be used with the chat/completions endpoint"). The example cannot run on any non-OpenAI model, so it is removed; the `modalities`/`audio` request options and the `images()`/`audio()` response accessors remain unchanged. The example enumeration in the README was updated accordingly.

## [1.9.0] - 2026-09-08
### Added
- **NEW**: Image resolution tiers - `addImageByUrl(String, OpenRouterImageDetail)` and `addImageByBase64(Path, OpenRouterImageDetail)` emit the `content[].image_url.detail` key (`auto`/`low`/`high`/`original`) on image content parts, for URL and base64 images alike. The key is only emitted when explicitly configured; the no-detail overloads behave exactly as before. Javadoc notes that `original` is an OpenRouter extension not present in the OpenAI Chat Completions spec and is downgraded to `high` on providers without an original-resolution tier. The tier survives the tool-call loop's follow-up requests (messages are carried verbatim - regression-tested).
- **NEW**: Response accessors for multimodal output on `OpenRouterChatCompletionResponse` - `images()` / `imageUrls()` surface `choices[0].message.images` (the URL/base64 payloads produced by image-generation models) and `audio()` / `audioId()` / `audioData()` / `audioExpiresAt()` / `audioTranscript()` surface `choices[0].message.audio` (id, base64 data, expiry, provider transcript). All follow the swallow-and-return-null/empty convention; javadoc notes the `modalities(...)` prerequisite.
- **NEW**: Response accessors for the logprobs round trip - `logprobs()` returns the raw `choices[0].logprobs` object (`content`/`refusal` arrays of per-token log probabilities) so the data requested via `logprobs(true)` / `topLogprobs(n)` becomes inspectable, and `systemFingerprint()` returns the top-level provider-side model snapshot.
- **NEW**: Examples for image resolution tiers (`OpenRouterChatCompletionWithVisionDetailExample`), logprobs (`OpenRouterChatCompletionWithLogprobsExample`), audio output (`OpenRouterChatCompletionWithAudioOutputExample`) and the streaming reasoning/refusal accessors (`OpenRouterChatCompletionStreamingReasoningExample`).

### Fixed
- **The streaming tool-call accumulator no longer drops the `reasoning`, `reasoning_details`, `refusal` and `audio` deltas.** The accumulator previously captured only `role`/`content`/`tool_calls` from each chunk's `delta`, so the synthetic response of the streaming loop reported an empty reasoning/refusal/audio side while the synchronous path exposed them - an asymmetry between the two execution paths of the same feature set. The deltas are now accumulated (reasoning and refusal as appended text; `reasoning_details` entries appended in arrival order; `audio` merged by concatenating `data` and `transcript` fragments and keeping the first `id`/`expires_at`) and the synthetic response exposes them through the existing accessors. Deliberate behaviour choice: reasoning and refusal deltas are still NOT forwarded as content chunks - the user handler keeps receiving content only; the accumulated values live on the synthetic response.
- **Chunk-level `service_tier`, `openrouter_metadata` and `system_fingerprint` are carried into the synthetic response of the streaming loop**, so `serviceTier()`, `openrouterMetadata()` and `systemFingerprint()` work on the streaming path too, matching the synchronous path. Previously they always returned `null` when streaming.

## [1.8.0] - 2026-09-07
### Added
- **NEW**: Predicted outputs support - `prediction(String)` / `predictionParts(String...)` / `predictionParts(List)` emit the `prediction` request object as `{"type":"content","content":...}` (string form wins when both are set) so supported models can reuse known content and answer faster. Response accessors `acceptedPredictionTokens()` / `rejectedPredictionTokens()` surface `usage.completion_tokens_details.accepted_prediction_tokens` / `rejected_prediction_tokens`.
- **NEW**: Prompt-caching controls at request root - `cacheControl()` / `cacheControl(String ttl)` emit `{"type":"ephemeral"[,"ttl":...]}` (automatic caching; supported by Anthropic, Google Vertex, Azure, Amazon Bedrock), `promptCacheKey(String)` emits the sticky-routing key `prompt_cache_key` (only used by OpenRouter when `session_id` is unset - precedence documented in the javadoc), and `promptCacheOptions(String mode)` / `promptCacheOptions(String mode, String ttl)` emit `{"mode":...[,"ttl":...]}` (e.g. `"explicit"` disables OpenAI-managed breakpoints).
- **NEW**: `reasoningSummary(String)` builder method - emits `reasoning.summary` (`auto`/`concise`/`detailed`) to control the verbosity of the reasoning summaries returned in `reasoning_details`; coexists with the existing reasoning options in one `reasoning` object.

- **NEW**: Examples for predicted outputs (`OpenRouterChatCompletionWithPredictionExample`), prompt caching (`OpenRouterChatCompletionWithPromptCachingExample`), capacity tiers (`OpenRouterChatCompletionWithServiceTierExample`) and the reasoning summary verbosity (added as example 5 to `OpenRouterChatCompletionWithThinkingExample`).

## [1.7.0] - 2026-09-06
### Added
- **NEW**: OpenRouter server tools in the `tools` array - `serverTools(OpenRouterServerTool...)` / `serverTools(List)` / `addServerTool(OpenRouterServerTool)`. Server tools are executed by OpenRouter itself (results arrive as `server_tool_calls`, no client-side callback) and are emitted as `{"type":"<server-tool-type>"[, "parameters":{...}]}` into the same `tools` array as the function tools, freely mixed with them. Typed implementations: `OpenRouterWebSearchServerTool` (`openrouter:web_search`; engine, max_results, max_total_results, max_uses, max_characters, mode, search_context_size, allowed/excluded domains plus a verbatim `option(key, value)` escape hatch), `OpenRouterWebFetchServerTool` (`openrouter:web_fetch`) and `OpenRouterDatetimeServerTool` (`openrouter:datetime`); `OpenRouterServerTool.of(String)` / `OpenRouterGenericServerTool` is the verbatim escape hatch for every other (or future) server-tool type. The `tool_choice` / `parallel_tool_calls` emission invariant is unchanged: both are emitted only when the tools array is non-empty (function or server tools).
- **NEW**: Server-tool `tool_choice` form - `toolChoiceServerTool(String)` emits `{"type":"<server-tool-type>"}` (e.g. `openrouter:web_search`, `web_search`, `web_search_preview`); the type string is accepted verbatim because the API schema is free-form here on purpose. Precedence when several forms are set: named function form (`toolChoiceFunction`) > server-tool form > plain string keywords (`toolChoice`). Documented in the javadoc.
- **NEW**: `stop_server_tools_when` support - `stopServerToolsWhen(OpenRouterStopCondition...)` / `stopServerToolsWhen(List)` / `addStopServerToolsWhen(...)`. Typed condition factories for all five schema types: `OpenRouterStopCondition.stepCountIs(int)`, `hasToolCall(String)`, `maxTokensUsed(long)`, `maxCost(double)` and `finishReasonIs(String)`, plus `raw(JSONObject)` as the verbatim escape hatch (requires a `type` field). The array is emitted only when at least one condition is set. Javadoc documents the API semantics: any condition firing halts the server-tool agent loop (OR logic), when set it overrides `max_tool_calls`, and a firing condition leads to one final turn with tools disabled so the answer ends in natural language.
- **NEW**: Examples for server tools with stop conditions (`OpenRouterChatCompletionWithServerToolsExample`), the server-tool `tool_choice` form (`OpenRouterChatCompletionWithServerToolChoiceExample`) and streaming error handling (`OpenRouterChatCompletionStreamingErrorExample`).

### Fixed
- **Mid-stream error chunks are no longer silently dropped by the streaming tool-call accumulator.** OpenRouter reports mid-generation failures as a regular `data:` event with a top-level `error` object inside an otherwise valid HTTP 200 stream; the accumulator previously ignored it, so a failed stream looked exactly like an empty one. The chunk-level `error` object is now captured and the synthetic response of the streaming loop exposes it through the existing accessors (`hasError()`, `error()`, `errorCode()`, `errorMessage()`), matching the synchronous path. Deliberate behaviour choice: the streaming loop finishes normally after an error chunk (content already streamed stays streamed) and exposes the failure via the accessors instead of throwing - `throwOnError()` remains the opt-in loud check. Chunks without an `error` field behave exactly as before.

## [1.6.0] - 2026-09-05

The provider-native finish reason is carried into `native_finish_reason` of the synthetic response as well.
- **NEW**: Examples for the web search plugin (`OpenRouterChatCompletionWithWebSearchPluginExample`), image output (`OpenRouterChatCompletionWithImageOutputExample`) and the response details (`OpenRouterChatCompletionWithResponseDetailsExample`).

## [1.5.0] - 2026-09-04
### Added
- **NEW**: App-attribution support - `OpenRouterAppAttribution` value type plus client-level configuration via `OpenRouterClient.appAttribution(...)`. The values travel as `HTTP-Referer` (app URL, primary identifier for the leaderboards), `X-OpenRouter-Title` (display name; the legacy `X-Title` header remains an accepted API alias, the library always sends the current one) and `X-OpenRouter-Categories` (at most 2 marketplace categories; more throw an `IllegalArgumentException`). Per-request overrides via the new `httpReferer(String)`, `appTitle(String)` and `appCategories(String...)` builder methods win over the client-level default.
- **NEW**: `models(String...)` / `models(List)` builder method - the fallback model list. The single `model` key is always emitted alongside; per the API semantics `models` acts as fallback candidates tried in order when the primary model cannot serve the request.
- **NEW**: Observability parameters: `metadata(Map)` / `addMetadata(String, String)` (up to 16 string key/value pairs, keys max 64 chars, values max 512 chars - validated up front), `user(String)` (stable per-end-user identifier for abuse isolation) and `sessionId(String)` (sticky-routing key for prompt-cache hits; sets the `x-session-id` header in addition to the `session_id` body field, which takes precedence).
- **NEW**: `metadataInResponse(boolean)` builder method - sends the `X-OpenRouter-Metadata: enabled` opt-in header so the response may carry routing metadata under `openrouter_metadata` (the legacy `X-OpenRouter-Experimental-Metadata` header remains an accepted API alias).
- **NEW**: Extended provider preferences, all emitted inside the existing `provider` object: `dataCollection(String)` (`provider.data_collection`, `"allow"`/`"deny"`), `ignoreProviders(String...)` / `addIgnoreProvider(String)` (`provider.ignore`), `onlyProviders(String...)` / `addOnlyProvider(String)` (`provider.only`), `maxPrice(String prompt, String completion[, String image, String audio])` (`provider.max_price`, prices as strings), `quantizations(String...)` (`provider.quantizations`), `sort(String)` (`provider.sort`: `"price"`, `"throughput"`, `"latency"`) and `enforceDistillableText(Boolean)` (`provider.enforce_distillable_text`). The `provider` object is emitted when any of the routing options - old or new - is set.
- **NEW**: Examples for app attribution (`OpenRouterChatCompletionWithAppAttributionExample`), model fallbacks (`OpenRouterChatCompletionWithModelFallbacksExample`), observability (`OpenRouterChatCompletionWithObservabilityExample`) and provider preferences (`OpenRouterChatCompletionWithProviderPreferencesExample`).

### Changed
- **Copy lists replaced by a copy factory**: the tool-call loop's follow-up requests were built from two hand-maintained option copy lists in `OpenRouterChatCompletionCallHandler` (`buildNextRequest` / `buildStreamingRequest`) - the structure that silently dropped `requireParameters`/`allowFallbacks` in 1.4.0 (defect D1) and was the reason every new option needed the error-prone "step 5" pass. Both methods now delegate to a new package-private `copyForNextTurn(...)` on `OpenRouterChatCompletionRequest`, which reads every private field of the same class directly, so a newly added option can no longer be forgotten on follow-up requests. Behaviour is unchanged (covered by the propagation regression tests, now extended to all new options and their headers).

This is a wire-format change of a published method, deliberately released as a **fix, not a breaking change**: the old format no longer exists in the OpenRouter API schema, so callers of `thinking()` have not received working reasoning behaviour to preserve - the request silently did not do what it said. Source and binary compatibility are fully intact; no code changes are required. The old JSON keys appear nowhere in the current OpenAPI schema (verified against https://openrouter.ai/openapi.yaml).

- `maxOutputTokens(Integer)` in favour of `maxCompletionTokens(Integer)`; `maxOutputTokens` keeps emitting the deprecated `max_tokens` key exactly as before - existing callers are unaffected, the deprecation only steers new code to the non-deprecated parameter.
- Accessor `thinkingBudget()` in favour of `reasoningMaxTokens()`; it keeps returning the same value.

### Fixed
- **Copy lists**: `requireParameters` and `allowFallbacks` were silently lost on follow-up requests of the tool-call loop (from turn 2 on), both synchronously and in streaming mode. The hand-maintained option copy lists in `OpenRouterChatCompletionCallHandler` now carry all options, and the copy methods are covered by tests.
- **Build**: `maven-surefire-plugin` is now pinned to 3.5.2. Maven's built-in default is 2.12.4, which cannot execute JUnit 5 tests: the suite reported `Tests run: 0` while the build stayed green, so no test in this project had ever actually run. The whole suite now executes (43 tests as of this release).
- **Build**: GPG signing moved into a `release` profile. It was bound to the `verify` phase, so `mvn verify` failed for anyone without a private signing key - every contributor and every CI run. Plain `mvn verify` now works without a key; releases use `mvn -Prelease deploy`.
- **Javadoc**: `OpenRouterResponse` was documented in German with unescaped generics, producing 14 `invalid input: '<'` warnings in the published javadoc jar. Rewritten in English with the generics escaped and the missing `@param <T>` added.
- **Javadoc**: `StreamingToolCallHandler` linked to `#onData(String)`, which does not exist on that type - `onData` is inherited as `onData(T)`. The link now resolves.
