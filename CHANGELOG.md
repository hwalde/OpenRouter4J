# Changelog

All notable changes to this project will be documented in this file.

## [1.30.0] - 2026-09-24
### Added
- **NEW**: OpenAI Responses-syntax web search shorthand on the chat `tools` array - `OpenRouterWebSearchShorthandTool` (also reachable as `OpenRouterServerTool.webSearchShorthand()`) emits the `web_search_preview` tool form that OpenRouter converts automatically to `openrouter:web_search`. Flat top-level fields per the OpenAI Responses syntax (no `parameters` wrapper): the configurable `type` discriminator (`web_search`, `web_search_preview` (default), `web_search_preview_2025_03_11`, `web_search_2025_08_26`, unknown values accepted verbatim), `engine`, `maxResults`, `maxTotalResults`, `maxUses`, `maxCharacters`, `mode`, `searchContextSize`, `allowedDomains` / `excludedDomains` (mutually exclusive - documented), `userLocation` (reuses `OpenRouterWebSearchPlugin.UserLocation`) and `xSearch` (reuses `OpenRouterWebSearchServerTool.XSearchOptions`), plus the verbatim `option(key, value)` escape hatch (covers the nested `parameters` object of `WebSearchConfig` and rejects `type`). The library emits the shorthand verbatim and never converts it - conversion is the API's job. Javadoc cross-references `OpenRouterWebSearchServerTool` as the canonical, strictly more expressive form. Example: `OpenRouterChatCompletionWithServerToolsExample`. Tests: 9 new tests (type-only emission, flat-field emission without a `parameters` wrapper, `excluded_domains` emission, both domain lists emitted verbatim when both are set - the library enforces nothing and leaves the rejection to the API, empty domain lists omit the fields, verbatim passthrough in the chat request body, escape-hatch emission with `type` rejection and explicit-JSON-null passthrough, custom type verbatim).
- **NEW**: Typed custom (freeform) tools on the Responses request - `OpenRouterCustomTool` emits `{"type":"custom","name":...}` for the client-executed tool that is not a JSON-schema function: `text(name)` / `text(name, description)` (no explicit `format` - the API default is plain text), `grammar(name, definition, syntax)` (the `{"type":"grammar","definition":...,"syntax":...}` form, `lark`/`regex` accepted verbatim) and the builder methods `description` / `formatText()` / `formatGrammar(definition, syntax)` (a later call replaces the whole format form) / `async(Boolean)` (`false` is a set option and is emitted) plus the verbatim `option(key, value)` escape hatch (rejects `type` and `name`). Usable via `addTool(...toJson())` on `client.responses()`. Deliberately **not** an `OpenRouterServerTool` implementation: the published schema declares `CustomTool` on the Responses `tools` array (and on the mid-input `additional_tools` item) and not on the chat-completions union, so the class cannot reach the chat builder's `serverTools(...)` by accident. Traps documented: `async: true` is only honored by providers whose Responses API supports async tools (ignored elsewhere), and the result must come back as a `function_call_output` with the original `call_id` in a later request - not as a per-turn tool reply. Example: `OpenRouterResponsesExample`. Tests: 11 new tests (text form with and without explicit `format` and the two-argument description factory, grammar form with both fields, `async(false)` emission, format-form replacement, blank-name/blank-definition/blank-syntax/option-hatch rejection, escape-hatch passthrough with explicit-JSON-null, presence in the Responses `tools` array, absence when no tool is added).
- **NEW**: Typed MCP server tool on the Responses request - `OpenRouterMcpServerTool.builder(serverLabel)` emits `{"type":"mcp","server_label":...}` for third-party Model Context Protocol tool servers: `serverUrl`, `connectorId` (free-form, the eight documented `connector_*` values named in the javadoc), `authorization`, `allowedTools(String...)` / `allowedTools(List)` (the array-of-names form) and `allowedToolsObject(readOnly, toolNames)` (the `{"read_only":...,"tool_names":[...]}` object form - the two forms replace each other, a null/empty part is omitted, both empty clears `allowed_tools` entirely), `headers(Map)` and `serverDescription`, plus the three `requireApproval` wire forms (bare `"always"`/`"never"` string - the schema declares no other values for that branch, verbatim `JSONObject`, or `requireApproval(boolean always, List toolNames)` building the object form where a null/empty list means "all tools" and omits `tool_names`) and the verbatim `option(key, value)` escape hatch (rejects `type` and `server_label`). Only explicitly configured fields are emitted (plus the required `type`/`server_label`). Flat top-level fields - this is not an `openrouter:*` namespace tool with a `parameters` wrapper. The published schema declares `McpServerTool` on the Responses `tools` array (and on the mid-input `additional_tools` item); the chat-completions `tools` union does not list it, so sending it through `serverTools(...)` is an escape-hatch use at the caller's risk. Example: `OpenRouterResponsesExample`. Tests: 15 new tests (type+label only when unset, only-configured-fields emission, both `allowed_tools` wire forms including the List overload, object-form partial-null/empty semantics, empty `allowed_tools`/`headers` omit the fields and clear a previously set value, form replacement in both directions, all three `require_approval` forms including the `never` variant, the empty-list "all tools" shape, `requireApproval((JSONObject) null)` unsetting a previous value and a full-structure verbatim passthrough, blank-label and option-hatch rejection, escape-hatch passthrough with explicit-JSON-null, presence in the Responses `tools` array).
- **NEW**: Three OpenAI-native server tools typed at last - `OpenRouterCodeInterpreterServerTool` (`code_interpreter`) with the required `container` in both wire forms (`container(String)` for the plain string, `containerAuto()` / `containerAuto(fileIds)` / `containerAuto(fileIds, memoryLimit)` for the `{"type":"auto"}` object with `file_ids` and `memory_limit`; the two-argument form always emits `memory_limit` - a `null` there is an explicit JSON `null` (this library's contract for "no explicit limit"), while the one-argument and no-argument forms omit the field so the API default applies; `memoryLimit` is validated against the documented enum `1g`/`4g`/`16g`/`64g`; `container(JSONObject)` is the verbatim form; a tool without a container is rejected loudly at `build()`), `OpenRouterComputerUseServerTool` (`computer_use_preview`) with the required `displayWidth` / `displayHeight` (positive, validated loudly) and `environment` (free-form per the schema, the five documented values `windows`/`mac`/`linux`/`ubuntu`/`browser` named in the javadoc; all three missing fields rejected loudly at `build()`), and `OpenRouterFileSearchServerTool` (`file_search`) with the required non-empty `vectorStoreIds` (blank entries rejected loudly), `maxNumResults`, `filter(key, operator, value)` (comparison filter with string/number/boolean/array values, operator accepted verbatim with the six documented values) plus `filters(JSONObject)` for the compound-filter escape hatch, and `ranker` / `scoreThreshold` composing `ranking_options`. Each implements `OpenRouterServerTool` with flat top-level fields (no `parameters` wrapper - these are OpenAI-native tool types) and a verbatim `option(key, value)` escape hatch that rejects the typed keys. The published schema declares all three on the Responses `tools` array (and on the mid-input `additional_tools` item); the chat-completions `tools` union does not list them, so sending them through `serverTools(...)` is an escape-hatch use at the caller's risk. Traps documented: code-interpreter output files are read back through `client.containers()` (list / download / promote), and `file_search` filters accept either a single comparison filter or a compound `and`/`or` filter. Example: `OpenRouterResponsesExample`. Tests: 24 new tests (string and auto-object container forms, the full `memory_limit` enum pinned plus typed explicit-null emission versus field omission, container forms replacing each other, verbatim container object, missing/invalid container and option-hatch rejection including a near-miss enum typo, all-three-required-fields emission and rejection for computer use including non-positive display sizes, the full option-hatch deny list and explicit-JSON-null passthrough, only-configured-fields emission for file search, comparison and array-valued filters, compound-filter escape hatch with full structure round-trip, filter-form replacement and `filters(null)` unset, `ranking_options` partial states, empty/blank `vector_store_ids` and option-hatch rejection, escape-hatch passthrough with explicit-JSON-null, presence in the Responses `tools` array, mixed `tools` array with a function tool and all five OpenAI-native tool types).
- Suite now 996 tests (59 new request-JSON level tests). All shapes follow the published OpenAPI schema (openapi.yaml, 2026-09-24); no live probing this round - every surface is a request-shape change with no new endpoint.

## [1.29.0] - 2026-09-24
### Added

Tests: 39 new tests (presence with all fields, absence when unset with forced provider object, provider-object emission invariant, plain-form/2-arg variants, sortBy precedence, preferredMaxLatency/preferredMinThroughput cutoffs emission and number-wins precedence, sortBy partition guard, quantizations empty-list clears, accessor round-trips) across the four endpoint test suites.

Example: `OpenRouterMessagesExample`. Tests: 9 new tests (presence/absence with and without cache_control, all three tool-reference forms, breakpoint-marker rejection, raw() passthrough + type-required, single-arg factories, system-role assertion, toolRemoval cache_control).
- **NEW**: `switchyard-router` plugin - `OpenRouterSwitchyardRouterPlugin` with `algorithm(String)` (free-form, the six documented values `capability`/`stage`/`auto`/`random`/`composite`/`passthrough` named in the javadoc; omitted = platform default `capability`) plus the `option(key, value)` escape hatch. - **NEW**: `x_search` on the web search plugin - `xSearch(OpenRouterWebSearchServerTool.XSearchOptions)` on `OpenRouterWebSearchPlugin` fills the `x_search` field that previously only existed on the `openrouter:web_search` server tool (typed in 1.28.0). - Suite now 937 tests (72 new request-JSON level tests including edge-case coverage for the 1.28.0 null-unset contracts). All shapes follow the published OpenAPI schema (openapi.yaml, 2026-09-24); no live probing this round - every surface is a request-shape change with no new endpoint.

## [1.27.0] - 2026-09-23
### Added
- **NEW**: `declared_zdr` on the BYOK create/update requests - `declaredZdr(Boolean)` on `client.byok().create()` and `client.byok().update(id)` plus the `OpenRouterByokKey.declaredZdr()` view accessor. The caller's self-declaration of whether the upstream provider account behind the credential has zero data retention: `true` declares the account ZDR so `zdr(true)`-routed requests (the credential-side counterpart of that request-side routing flag) may use the credential even when the shared endpoint retains data; `false` declares it non-ZDR so they never do (`false` is a set option and is emitted); `null` emits an explicit JSON `null`. Tri-state per request, documented in the javadoc: on create, unset (key omitted) and explicit `null` both mean "inherit OpenRouter's data policy for the provider's endpoint" (the API default); on update they differ - unset leaves the stored value unchanged, while explicit `null` clears the declaration back to inherit. Self-declared, not verified by OpenRouter. Example: `OpenRouterByokExample`. Tests: 4 new tests (create true/false/explicit-null/unset, update true/false/explicit-null/unset with the omit-vs-null distinction and exact single-key bodies, set-twice replace on both builders, three-state view accessor incl. `false` and JSON-null).
- **NEW**: `processing` on the chat `video_url` content part - `addVideoByUrl(url, OpenRouterVideoProcessing)` emits the video input's `processing` field (`AGENTIC` = agentic video processing, `STATIC` = fixed-rate frame sampling, currently Google Gemini only), emitted only when set; the single-argument `addVideoByUrl(url)` stays byte-identical (provider default, no `processing` key). The enum is `OpenRouterVideoProcessing` (mirroring `OpenRouterImageDetail`). Trap documented: the mode is provider-dependent, and the same field exists on the legacy `input_video` variant, which has no typed helper (`addContentPart(JSONObject)` covers it). Example: `OpenRouterChatCompletionWithFileAudioVideoExample`. Tests: 2 new/updated tests (presence per mode, absence when unset - the single-arg case now asserts the key is absent).
- **NEW**: Object forms of `tool_choice` on the Responses request - the union members of `OpenAIResponsesToolChoice` that the plain `toolChoice(String)` keyword could not express: `toolChoiceFunction(name)` emits the named function form `{"type":"function","name":...}` (flat `name`, deliberately not the chat-completions nested `function.name` shape), `toolChoiceAllowedTools(mode, toolRefs...)` / `toolChoiceAllowedTools(mode, Collection)` emit `{"type":"allowed_tools","mode":"auto"|"required","tools":[...]}` (each ref a `String` shorthand for `{"type":"function","name":...}` or a verbatim `JSONObject`; mode and at least one ref validated loudly; a later call replaces the whole form) and `toolChoiceType(type)` emits the tool-type shorthand `{"type":...}` (documented variants `web_search_preview`, `web_search_preview_2025_03_11`, `apply_patch`, `shell`; accepted verbatim as an escape hatch). Read-back accessors `toolChoice()` (raw keyword, non-null also when shadowed by an object form) / `toolChoiceFunctionName()` / `toolChoiceAllowedToolsMode()` / `toolChoiceAllowedTools()` / `toolChoiceType()`. Precedence when several forms are set (javadoc + `getBody()`): named function > allowed_tools > tool-type > plain string keyword. Unlike the chat builder, `tool_choice` is emitted whenever a form is set, even when `tools` is empty. Trap documented per method: with deferred tools (`openrouter:tool_search` + top-level `defer_loading`) `tool_choice` must stay unset, `"auto"` or `allowed_tools` - any other setting makes the request fail. Also rewrote the now-false "this library does not offer `allowed_tools`" notes on `OpenRouterToolSearchServerTool` / `OpenRouterToolDefinition.deferLoading` / `OpenRouterChatCompletionWithToolSearchExample` to point at `toolChoiceAllowedTools`. Example: `OpenRouterResponsesExample` (one request per form). Tests: 5 new tests (exact emission per form including a non-function verbatim ref, precedence chain with the raw keyword read-back, unset-direction accessors, replace-not-append, invalid-argument rejection).
- **NEW**: Typed `classifier_dimensions` and `classifier_filters` on the analytics query request - the two `POST /analytics/query` extensions that so far only had the verbatim `option(key, value)` escape hatch: `classifierDimensions(classifierId, dimensionNames...)` emits `{"classifier_dimensions":{"classifier_id":...,"dimension_names":[...]}}` (at most two names in total across calls, count validated loudly, null/empty names skipped; with no names the response uses the `clf_dimension_name`/`clf_dimension_value` columns), `classifierIncludeNulls(Boolean)` adds `include_nulls` to that object (`false` is a set option and is emitted; API default `false` = only classified generations), `classifierFilters(classifierId)` plus `classifierFilter(field, operator, value)` (scalar string or number overload, `eq`/`neq`) and `classifierFilterIn(field, operator, values)` (array form, `in`/`not_in`) emit `{"classifier_filters":{"classifier_id":...,"filters":[...]}}` (1-10 entries, validated loudly). The request exposes the read-back accessors `classifierDimensionsId()` / `classifierDimensionNames()` / `classifierIncludeNulls()` / `classifierFiltersId()` / `classifierFilters()`. Order of the calls does not matter. Cross-field trap (javadoc + loud `build()` check): when both objects are configured they must carry the same `classifier_id` - the API rejects a mismatch. Loud validation also covers incomplete combinations (filters without id, id without entries, `include_nulls` without `classifierDimensions`), a re-set of either id to a different value, null/empty field, operator or value arguments, and the operator/`value`-shape pairing. ## [1.26.0] - 2026-09-23
### Added
- **NEW**: Vault secrets API - the `client.vault()` surface for the host-bound secrets of the active workspace and of interns: `list()` (GET /vault/secrets with `limit` 1-100, API default 100, and `offset` 0-10,000, both validated loudly), `store(name)` (PUT /vault/secrets/{name}; `value` 1-65,536 characters and `hosts` 1-100 entries, both required and validated loudly for the cheap local rules), `delete(name)` (DELETE, 204 with no body, 404 for unknown names), the intern counterparts `internSecrets(internId)` / `storeInternSecret(internId, name)` / `deleteInternSecret(internId, name)` and the copy route `copySecretsToIntern(internId).names(...)` (POST /vault/interns/{internId}/secrets/copy; 1-100 distinct names, validated loudly). The shared `OpenRouterVaultSecret` view exposes the metadata `name`, `hosts`, `fingerprint` (`sha256:...`) and `createdAt`, with `hasMore()` on the list responses. **Metadata-only rule**: the plaintext value is encrypted at rest and never returned by any vault response - treat it as a write-only secret; the store requests' `toString()` never contains it. Traps documented in the javadoc: the fingerprint is comparable only within one vault (equal fingerprints mean equal values; copies in another vault carry different fingerprints and a workspace rotation does not propagate); hosts are normalized server-side (lowercased, trailing dot removed) and matched exactly at release time; every requested copy name must exist or the API answers 404 and copies nothing (409 when a source secret has `hosts: null` or the intern is mid-transfer); writes can answer 503 while vault writes are disabled per account; the scope is selected by the API key's active workspace (no workspace parameter, no fallback); every vault route, including the list, answers 404 outside the Intern API programme. Not yet live-verified (probing mutates account state). Example: `OpenRouterVaultExample`. Tests: 17 new tests (request-JSON, URL shape, validation, response fixtures) plus an entry-point test in the client entry-point suite.
- **NEW**: Interns API (the OpenRouter "Ori" programme) - the `client.interns()` surface: `list()` (GET /interns, newest first, with the typed filters `limit` 1-500, lifecycle `status` (comma-separated, at most 8, repeats collapsed), the `starting_after` cursor plus the verbatim `queryParam` escape hatch), `create(name)` (POST /interns; name pattern `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` 2-17 chars validated loudly; optional `workspaceId`, `description`, `instructions`, `provision(true)` and a borrowed `vaultId`; the optional `Idempotency-Key` header via `idempotencyKey(String)`; body capped at 1 MiB), `get(internId)`, `update(internId)` (PATCH; `name`/`description`/`instructions`/`model` each emitted only when set, omitted fields stay unchanged), `delete(internId)` (safe teardown with the optional `acknowledgeWorkspaceLoss(true)` consent, answers 202 `deleting`), `provision(internId)` (first boot or resume, 202 `provisioning`) and `suspend(internId)` (stop the runtime, keep disk and configuration). The typed `OpenRouterIntern` view covers the lifecycle status, `progress` (`stepNumber`/`totalSteps`/`stepLabel`), `hostname`, `vaultId`/`attachedVaultId` and `lastFailureMessage`. Streaming chat: `chat(internId)` issues POST /interns/{internId}/chat/completions in the OpenAI chat-completions SSE format - the endpoint only streams, so the builder refuses a request without an installed streaming handler; only the last message is read (`addUserMessage`, `addEchoedAssistantMessage` for the documented tool-call echo and `addToolReply(id, content|JSONObject)` for the answer; a tool reply requires `sessionId` and is validated loudly); there is deliberately no `model` builder method (accepted by the API but never used). The `OpenRouterInternChatAccumulator` handler forwards every raw chunk and accumulates the interaction loop's pieces with typed accessors: `finishReason()` (`stop`/`tool_calls`/`error`), `isInteractionPending()`, the `openrouter.provide_input` `toolCall()` (id, name, arguments with `argumentsJson()`), `sessionId()` from the final empty-`choices` chunk, the concatenated `text()`/`reasoning()`, the streamed error (`errorCode()`/`errorReason()`/`errorRetryable()`) and the usage accessors. Traps documented in the javadoc: a paused run waits 5 minutes (answering afterwards is rejected with `409 interaction_not_pending`); closing an active stream cancels the run; streamed failures arrive as a `finish_reason: "error"` chunk with `error.metadata.reason`; heartbeats travel as SSE comment lines the processor ignores; every path answers 404 outside the interns programme; a message on a session with a running turn can be answered with a non-streamed 202 `{"status":"steered"}` body (exposed by `OpenRouterInternChatResponse.isSteered()`). ### Added
- **NEW**: OpenRouter server tools in the `tools` array - `serverTools(OpenRouterServerTool...)` / `serverTools(List)` / `addServerTool(OpenRouterServerTool)`. Server tools are executed by OpenRouter itself (results arrive as `server_tool_calls`, no client-side callback) and are emitted as `{"type":"<server-tool-type>"[, "parameters":{...}]}` into the same `tools` array as the function tools, freely mixed with them. Typed implementations: `OpenRouterWebSearchServerTool` (`openrouter:web_search`; engine, max_results, max_total_results, max_uses, max_characters, mode, search_context_size, allowed/excluded domains plus a verbatim `option(key, value)` escape hatch), `OpenRouterWebFetchServerTool` (`openrouter:web_fetch`) and `OpenRouterDatetimeServerTool` (`openrouter:datetime`); `OpenRouterServerTool.of(String)` / `OpenRouterGenericServerTool` is the verbatim escape hatch for every other (or future) server-tool type. The `tool_choice` / `parallel_tool_calls` emission invariant is unchanged: both are emitted only when the tools array is non-empty (function or server tools).
- **NEW**: Server-tool `tool_choice` form - `toolChoiceServerTool(String)` emits `{"type":"<server-tool-type>"}` (e.g. `openrouter:web_search`, `web_search`, `web_search_preview`); the type string is accepted verbatim because the API schema is free-form here on purpose. Precedence when several forms are set: named function form (`toolChoiceFunction`) > server-tool form > plain string keywords (`toolChoice`). Documented in the javadoc.
- **NEW**: `stop_server_tools_when` support - `stopServerToolsWhen(OpenRouterStopCondition...)` / `stopServerToolsWhen(List)` / `addStopServerToolsWhen(...)`. Typed condition factories for all five schema types: `OpenRouterStopCondition.stepCountIs(int)`, `hasToolCall(String)`, `maxTokensUsed(long)`, `maxCost(double)` and `finishReasonIs(String)`, plus `raw(JSONObject)` as the verbatim escape hatch (requires a `type` field). The array is emitted only when at least one condition is set. Javadoc documents the API semantics: any condition firing halts the server-tool agent loop (OR logic), when set it overrides `max_tool_calls`, and a firing condition leads to one final turn with tools disabled so the answer ends in natural language.
- **NEW**: Examples for server tools with stop conditions (`OpenRouterChatCompletionWithServerToolsExample`), the server-tool `tool_choice` form (`OpenRouterChatCompletionWithServerToolChoiceExample`) and streaming error handling (`OpenRouterChatCompletionStreamingErrorExample`).

### Fixed
- **Mid-stream error chunks are no longer silently dropped by the streaming tool-call accumulator.** OpenRouter reports mid-generation failures as a regular `data:` event with a top-level `error` object inside an otherwise valid HTTP 200 stream; the accumulator previously ignored it, so a failed stream looked exactly like an empty one. The chunk-level `error` object is now captured and the synthetic response of the streaming loop exposes it through the existing accessors (`hasError()`, `error()`, `errorCode()`, `errorMessage()`), matching the synchronous path. Deliberate behaviour choice: the streaming loop finishes normally after an error chunk (content already streamed stays streamed) and exposes the failure via the accessors instead of throwing - `throwOnError()` remains the opt-in loud check. Chunks without an `error` field behave exactly as before.

## [1.6.0] - 2026-09-05
### Added
- **NEW**: Server-side plugins support - `plugins(OpenRouterPlugin...)` / `plugins(List)` / `addPlugin(OpenRouterPlugin)` builder methods emitting the `plugins` request array (behind a null/empty check). `OpenRouterWebSearchPlugin` is the typed implementation of the `web` plugin (engine, max_results, max_uses, mode, search_prompt, include/exclude_domains, approximate user_location - only explicitly configured fields are emitted); `OpenRouterGenericPlugin` / `OpenRouterPlugin.of(String)` is the verbatim escape hatch for every other plugin id (or ids added by OpenRouter later). Javadoc documents the interaction with `tool_choice`: web search results reach the model as server-executed tool calls (`server_tool_calls`), so plugins and client-side tools are two independent tool-call flows.
- **NEW**: Multimodal output support - `modalities(String...)` / `modalities(List)` / `addModality(String)` (`modalities` request array selecting `text` / `image` / `audio`) and `imageConfig(OpenRouterImageConfig)` (`image_config`; typed conveniences for `num_images`, `aspect_ratio`, `resolution`, `quality` plus a verbatim `option(key, value)` escape hatch, since the API defines it as provider-specific free-form keys). Without `modalities("...", "image")`, image-output models never produce images.
- **NEW**: Response accessors for OpenRouter-specific fields on `OpenRouterChatCompletionResponse`: `reasoning()` and `reasoningDetails()` (chain-of-thought output), `nativeFinishReason()` (provider-native finish reason next to the normalised one), `provider()` (which provider served the request) and `openrouterMetadata()` (routing metadata, present only with the `metadataInResponse(true)` opt-in).
- **NEW**: Loud error path on `OpenRouterChatCompletionResponse`: `hasError()`, `error()`, `errorCode()`, `errorMessage()` and `throwOnError()`. OpenRouter reports mid-request failures as a top-level `error` object inside an otherwise valid HTTP 200 response; because the accessors swallow exceptions and return `null`, such a response previously looked like an *empty* one. The existing "swallow and return null" convention of the other accessors is deliberately unchanged - `throwOnError()` is the opt-in loud check.
- **NEW**: Usage extras on `OpenRouterChatCompletionResponse`: `cost()` (USD, `usage.cost`), `costDetails()` (`usage.cost_details`), `cachedPromptTokens()` (`usage.prompt_tokens_details.cached_tokens`) and `reasoningTokens()` (`usage.completion_tokens_details.reasoning_tokens`).
- **NEW**: The streaming tool-call accumulator now captures the terminal usage chunk (OpenRouter emits one final chunk with an empty `choices` array and a `usage` object; previously it was silently dropped) and exposes it on the synthetic response of the streaming loop, so `cost()` and the token accessors work on the streaming path too. The provider-native finish reason is carried into `native_finish_reason` of the synthetic response as well.
- **NEW**: Examples for the web search plugin (`OpenRouterChatCompletionWithWebSearchPluginExample`), image output (`OpenRouterChatCompletionWithImageOutputExample`) and the response details (`OpenRouterChatCompletionWithResponseDetailsExample`).

## [1.5.0] - 2026-09-04
### Added
- **NEW**: App-attribution support - `OpenRouterAppAttribution` value type plus client-level configuration via `OpenRouterClient.appAttribution(...)`. The values travel as `HTTP-Referer` (app URL, primary identifier for the leaderboards), `X-OpenRouter-Title` (display name; the legacy `X-Title` header remains an accepted API alias, the library always sends the current one) and `X-OpenRouter-Categories` (at most 2 marketplace categories; more throw an `IllegalArgumentException`). Per-request overrides via the new `httpReferer(String)`, `appTitle(String)` and `appCategories(String...)` builder methods win over the client-level default.
- **NEW**: `models(String...)` / `models(List)` builder method - the fallback model list. The single `model` key is always emitted alongside; per the API semantics `models` acts as fallback candidates tried in order when the primary model cannot serve the request.
- **NEW**: Observability parameters: `metadata(Map)` / `addMetadata(String, String)` (up to 16 string key/value pairs, keys max 64 chars, values max 512 chars - validated up front), `user(String)` (stable per-end-user identifier for abuse isolation) and `sessionId(String)` (sticky-routing key for prompt-cache hits; sets the `x-session-id` header in addition to the `session_id` body field, which takes precedence).
- **NEW**: `metadataInResponse(boolean)` builder method - sends the `X-OpenRouter-Metadata: enabled` opt-in header so the response may carry routing metadata under `openrouter_metadata` (the legacy `X-OpenRouter-Experimental-Metadata` header remains an accepted API alias).
- **NEW**: Extended provider preferences, all emitted inside the existing `provider` object: `dataCollection(String)` (`provider.data_collection`, `"allow"`/`"deny"`), `ignoreProviders(String...)` / `addIgnoreProvider(String)` (`provider.ignore`), `onlyProviders(String...)` / `addOnlyProvider(String)` (`provider.only`), `maxPrice(String prompt, String completion[, String image, String audio])` (`provider.max_price`, prices as strings), `quantizations(String...)` (`provider.quantizations`), `sort(String)` (`provider.sort`: `"price"`, `"throughput"`, `"latency"`) and `enforceDistillableText(Boolean)` (`provider.enforce_distillable_text`). The `provider` object is emitted when any of the routing options - old or new - is set.
- **NEW**: Examples for app attribution (`OpenRouterChatCompletionWithAppAttributionExample`), model fallbacks (`OpenRouterChatCompletionWithModelFallbacksExample`), observability (`OpenRouterChatCompletionWithObservabilityExample`) and provider preferences (`OpenRouterChatCompletionWithProviderPreferencesExample`).

### Changed
- **Copy lists replaced by a copy factory**: the tool-call loop's follow-up requests were built from two hand-maintained option copy lists in `OpenRouterChatCompletionCallHandler` (`buildNextRequest` / `buildStreamingRequest`) - the structure that silently dropped `requireParameters`/`allowFallbacks` in 1.4.0 (defect D1) and was the reason every new option needed the error-prone "step 5" pass. Both methods now delegate to a new package-private `copyForNextTurn(...)` on `OpenRouterChatCompletionRequest`, which reads every private field of the same class directly, so a newly added option can no longer be forgotten on follow-up requests. Behaviour is unchanged (covered by the propagation regression tests, now extended to all new options and their headers).

## [1.4.0] - 2026-09-03
### Added
- **NEW**: `reasoningEffort(String)`, `reasoningMaxTokens(Integer)`, `reasoningExclude(Boolean)` and `reasoningEnabled(Boolean)` builder methods - configure reasoning via the current `reasoning` object format (`effort`, `max_tokens`, `exclude`, `enabled`). See the Changed entry below for the replaced wire format.

### Changed
- `thinking(Integer)` no longer sends the obsolete `"reasoning": {"type": "enabled", "budget": N}` shape. It now emits `"reasoning": {"max_tokens": N}`. This is a wire-format change of a published method, deliberately released as a **fix, not a breaking change**: the old format no longer exists in the OpenRouter API schema, so callers of `thinking()` have not received working reasoning behaviour to preserve - the request silently did not do what it said. Source and binary compatibility are fully intact; no code changes are required. The old JSON keys appear nowhere in the current OpenAPI schema (verified against https://openrouter.ai/openapi.yaml).

### Deprecated
- `thinking(Integer)` in favour of `reasoningMaxTokens(Integer)` (same emission, current name).
- `maxOutputTokens(Integer)` in favour of `maxCompletionTokens(Integer)`; `maxOutputTokens` keeps emitting the deprecated `max_tokens` key exactly as before - existing callers are unaffected, the deprecation only steers new code to the non-deprecated parameter.
- Accessor `thinkingBudget()` in favour of `reasoningMaxTokens()`; it keeps returning the same value.

### Fixed
- **Copy lists**: `requireParameters` and `allowFallbacks` were silently lost on follow-up requests of the tool-call loop (from turn 2 on), both synchronously and in streaming mode. The hand-maintained option copy lists in `OpenRouterChatCompletionCallHandler` now carry all options, and the copy methods are covered by tests.
- **Build**: `maven-surefire-plugin` is now pinned to 3.5.2. Maven's built-in default is 2.12.4, which cannot execute JUnit 5 tests: the suite reported `Tests run: 0` while the build stayed green, so no test in this project had ever actually run. The whole suite now executes (43 tests as of this release).
- **Build**: GPG signing moved into a `release` profile. It was bound to the `verify` phase, so `mvn verify` failed for anyone without a private signing key - every contributor and every CI run. Plain `mvn verify` now works without a key; releases use `mvn -Prelease deploy`.
- **Javadoc**: `OpenRouterResponse` was documented in German with unescaped generics, producing 14 `invalid input: '<'` warnings in the published javadoc jar. Rewritten in English with the generics escaped and the missing `@param <T>` added.
- **Javadoc**: `StreamingToolCallHandler` linked to `#onData(String)`, which does not exist on that type - `onData` is inherited as `onData(T)`. The link now resolves.
